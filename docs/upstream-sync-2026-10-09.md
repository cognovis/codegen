## The open-target validation defect

Independent verification of the `0.3.0` candidate returned FAIL on the defect that stood as entry 3 above. Documenting it was not enough, so it is fixed, and the fix is a fork delta in generator sources — a pending upstream contribution, never an overlay path.

What the verifier observed, against the packed `@cognovis/codegen@0.3.0` tarball installed into a clean project and used to generate US Core TypeScript: `Provenance.target` of `[{reference: "Organization/org-1"}]` produced one validation error and `from()` threw, where the pre-merge fork (`8fd1a788`) reported nothing and returned. The same for `Organization` after a permitted `Patient`. `[{reference: "Patient/patient-1"}]` passed in both. Generation and compilation were never affected — all 67 generated modules typecheck strict NodeNext — so this was purely a runtime `validate()`/`from()` regression, reproducing in the shipped example, with the Python example showing the same shape for a `Practitioner` target.

The cause, confirmed: FHIR declares `Provenance.target` as `Reference(Any)`, whose declared target is the abstract `Resource`. `populateEffectiveReferences` sets `effectiveResource` from `expandAbstractTargets`, which replaces an abstract target with `schema.typeFamily.resources` — the concrete resources **present in the index**. Under tree shaking that is a subset of FHIR's resources, so `referenceAllowedTypes` returned a closed six-element list and both writers emitted it as a constraint. Before `b7ec6cde` this was invisible for repeating elements, because the helper read `.reference` off the array itself, got `undefined`, and checked nothing. Upstream's fix to read every entry is correct and is kept; the defect was that an **open** declared target set was rendered as a **closed** allow-list.

The fix is at the validation seam only. `referenceAllowedTypes` in `src/typeschema/utils.ts` now returns nothing when any declared target is abstract or a family root, and both writers already emit a check only for a non-empty list, so one change covers TypeScript and Python. `expandAbstractTargets` and `effectiveResource` keep their semantics deliberately: the type side consumes them, and it already treats a family target as open — `Provenance.target` generates as `Reference<string /* Resource */>[]`, which `CLAUDE.md` documents. Only validation disagreed, and now it does not. A genuinely closed declared target set is still enforced, on every entry: `Observation.performer` keeps `["CareTeam","Organization","Patient","Practitioner","PractitionerRole","RelatedPerson"]` in both languages.

This supersedes the validation half of the fork's own #242, which expanded the family into the allow-list to stop `["Resource"]` rejecting everything. That diagnosis was right about the symptom and the expansion remains correct for the types; the allow-list was the wrong place to spend it. The whole generated-output change is two lines: the `target` check disappears from the TypeScript and Python US Core Provenance profiles. Nothing else in any example moved, which `make all` confirms.

One pre-existing wart this makes visible but does not introduce: the TypeScript writer imports the validate-helper block wholesale whenever a profile has fields, so `Provenance_USCoreProvenance.ts` now imports `validateReference` without calling it. The base commit already did this elsewhere — `Extension_USCoreRaceExtension.ts` imported it unused — and `noUnusedLocals` is off, so it compiles. The Python writer tracks helpers per use, which is why its import list did shrink. Narrowing the TypeScript import block is a separate change that would churn many generated files, so it is left alone.

## Release-safety defects this synchronization exposed

Preparing this integration's release surfaced two defects in the release path. The first, below, would have published a backwards `latest`; the second, after it, would have rewritten committed changelog history on every release. Both are repaired.

### Backwards version derivation

Deriving the release version for this integration surfaced a defect that would have published a backwards `latest`. It is recorded here rather than as a standing fork bug because **the synchronization is what makes it reachable**: the trigger is upstream's release tags arriving in this repository, which only happens once a sync runs.

The reproduction, in this worktree:

- `git ls-remote --tags origin` carries none of `v0.0.16`…`v0.0.21`; `git ls-remote --tags upstream` carries all six. They are local now, so `git tag --list` interleaves upstream's `v0.0.2`…`v0.0.21` with the fork's `v0.1.0`…`v0.2.4`.
- This is not an artefact of how they were fetched. `scripts/sync-upstream.sh:99` runs a plain `git fetch "${UPSTREAM_REMOTE}"` with no `--no-tags`, and git by default fetches tags reachable from the fetched refs, so every documented synchronization brings upstream's release tags in.
- `cliff.toml` set no `tag_pattern`, so git-cliff ranked all of them as this project's releases and `--bumped-version` answered **`v0.0.22`** — derived from upstream's line, not the fork's.
- `scripts/release.sh` run without a version argument took that value, stripped the `v`, passed its own semver regex (`0.0.22` is well-formed), set `package.json` to `0.0.22`, committed `chore: bump version to 0.0.22`, tagged `v0.0.22` and pushed. `.github/workflows/release.yml` then publishes with `npm publish --tag latest`, which would have moved `latest` on npm.cognovis.de **backwards** from the published `0.2.4` to `0.0.22` — every consumer resolving `latest` would have been handed older code.

Repaired in both halves, so neither a tag-selection mistake nor any other derivation bug can reach the registry.

**Correctness** — `cliff.toml` gained a `tag_pattern` confining derivation to the fork's own lineage: `^v(0\.[1-9][0-9]*\.[0-9]+|[1-9][0-9]{0,2}\.[0-9]+\.[0-9]+)(-[0-9A-Za-z.-]+)?$`. Upstream's `v0.0.*` line can never match, because its minor is `0` and the first alternative requires a minor of `1` or more. The calendar tags `v2026.04.*` cannot match either, because a major is at most three digits. Tags that are not shaped like `v<semver>` — `cognovis/v2026.05.0`, `archive/2026-04-mira-adapters`, `untagged-54dea28f6361748d133f` — fail the anchor. It stays future-proof in the directions that matter: `v0.3.0`, `v0.10.0`, `v1.0.0`, `v2.17.3`, `v999.1.0` and prerelease forms such as `v0.3.0-rc.1` are all considered. Before the change git-cliff considered 31 versions, topped by `v0.0.21`; after it, it considers exactly `v0.1.0`, `v0.1.1`, `v0.2.0`, `v0.2.1`, `v0.2.2`, `v0.2.3`, `v0.2.4`, and `--bumped-version` answers `v0.2.5` — forward from the published stable, as it should be. (The delivery owner independently chose `0.3.0` for this release; the derivation says `0.2.5` only because the conventional commits since `v0.2.4` are fixes, docs and CI rather than features.)

**Safety net** — `scripts/release.sh` now refuses any version that does not strictly exceed the `package.json` version it replaces, before it writes anything, on both the derived and the explicit-argument path. The comparison implements semver precedence rather than string or version-sort order, so a prerelease correctly ranks below the release of the same core version, and it fails closed: a version neither side can parse is not treated as progress. Observed behaviour, exercised directly without tagging or pushing — `0.0.22` rejected, `0.2.4` rejected as not strictly greater, `0.2.4-rc.1` rejected, `0.2.5` and `0.3.0` accepted (each then stopping at the pre-existing main-branch check, which is left intact along with the clean-tree check).

A note on reproducing this. `scripts/release.sh` used to resolve git-cliff by preferring whatever `command -v git-cliff` found; on this host that is a version-manager shim for a tool that is not installed, which errors on invocation. Because the derivation discarded stderr, the derived version came out **empty** instead of `v0.0.22`, and the pre-existing semver regex rejected it — the defect was masked here while remaining live on any host or runner where git-cliff resolves properly. The `v0.0.22` derivation is therefore reproduced with `npx --yes git-cliff@2.14.2`. That masking is itself repaired, below.

### The changelog regeneration was destructive

Checking that the `0.3.0` changelog section would be purely additive showed that it would not be: `scripts/release.sh` generated the changelog with `--tag "v$VERSION" -o CHANGELOG.md`, a **full regeneration**, which rewrote 2430 lines of already-committed history. Two independent causes, either of which rewrites the file on its own:

- **No commit preprocessing.** `cliff.toml` carries `commit_preprocessors = []` since `29b55443 chore: remove retired tracker changelog preprocessing`. The committed `CHANGELOG.md` predates that removal and was generated with the tracker IDs stripped, so a regeneration reintroduces them into historical entries — `- Refresh generated resource descriptors` becomes `- **fmgt-thqw:** Refresh generated resource descriptors`, and `fmgt-qgrx` and `fmgt-4bg` likewise. Measured alone, against the pre-`tag_pattern` configuration, this accounts for 824 rewritten lines. Letting a release undo that deliberate decision as a side effect is not acceptable collateral.
- **Inherited sections become unrecognized.** The `tag_pattern` above deliberately excludes upstream's `v0.0.*` line, so the 11 inherited sections `0.0.2` through `0.0.12` lose their tags and their commits collapse into `0.1.0`. No content is lost, but 11 section headers disappear and `0.1.0` swells. This is why restoring `commit_preprocessors` alone could not fix the regeneration: the structure would still be rewritten.

Repaired by making the documented path additive instead: `scripts/release.sh` now runs `$CLIFF --unreleased --tag "v$VERSION" --prepend CHANGELOG.md`, which generates only the unreleased commits and prepends them. Neither cause can reach committed history any more, because committed history is no longer regenerated. Proven on the `0.3.0` section this release adds: excising it from the resulting `CHANGELOG.md` leaves a zero-line diff against the previously committed file.

The resolver was repaired in the same change, so the documented path is actually usable and cannot fail quietly. `scripts/release.sh` now probes that the git-cliff it found really runs (`git-cliff --version`) before trusting it, falls back to the pinned `npx --yes git-cliff@2.14.2` — pinned so that a release cannot silently change changelog tooling — and exits with a clear message if neither works. It also no longer discards the derivation's stderr, and fails loudly rather than continuing with an empty version. On this host it selects the pinned fallback and reports `git-cliff 2.14.2`, and the derivation answers `0.2.5` where it previously answered nothing.

## Residual risk

The Canonical Manager shared-cache caveat is carried forward unchanged and was **not** re-measured against `0.0.28`. Builders with isolated `forceDependencies` maps still share Canonical Manager's on-disk cache, whose key did not include patches at `0.0.26`; successive builders with identical roots and the same working directory can reuse the first patched manifest. The published `0.0.28` package ships no changelog, so no claim is made either way. Callers that change pin maps between runs still need separate working directories or a cache reset.

The reference-projection limitation recorded for PR #227 no longer reaches runtime validation. Family expansion is still effective only while the required family membership remains in the TypeSchema index, and tree shaking still narrows it — but that narrowed set is no longer emitted as a validation constraint, so it can no longer reject data the profile permits. See "The open-target validation defect" above. What remains of the limitation is confined to the generated *types*, where a family target is rendered open (`string /* Resource */`) and therefore does not constrain either.

Two further things are deliberately not covered here. The registry artifact and the real cognovis-fhir consumer generation — acceptance criteria 3 and 4 of the work order — are a separate release step; this report covers the integration only, and the published `latest` dist-tag and all consumer pins are untouched. And `upstream/main` is ahead of `v0.0.21`: integrating the released tag means the commits after it remain a later synchronization's subject.

Those deferred commits are no longer unexamined, and one of them carries a known cost. `v0.0.21..b16a0952` is 7 commits: `12d218c2` (the `bun audit fix` whose lock change this integration has now adopted on its own), `94e16e3f` and `7d37f4be` (translate, transform and hash each shared schema once, keyed by package and URL), `eb75aa9c` and `b16a0952` (generator-test cleanup). None of them touches the virtual R4 `Base` behaviour, so deferring them costs this integration nothing on that front. But `94e16e3f` and `7d37f4be` **rewrite `src/typeschema/index.ts` and `src/typeschema/register.ts`**, and `src/typeschema/index.ts` is one of the fork's 12 retained-delta files — it holds the shared-canonical rejection. The next synchronization will therefore conflict there, in a file whose fork delta exists precisely to make duplicate canonicals across concrete package versions fail. Plan that merge around the retained behaviour rather than around the diff: upstream is restructuring how `schemasWithSources` is built and hashed, which is the same collection the fork's conflict detection iterates.
